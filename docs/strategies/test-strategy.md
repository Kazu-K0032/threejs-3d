# テスト戦略

このプロジェクトで、何をどこまでテストで確かめ、何を人が確かめるかを決める。AI が書いたコードを、人が全部は読み切れなくても、壊れていないと言える状態を保つため。

## 採用する戦略

テストピラミッドを採る。小さく速い単体テストを土台に多く置き、結合テストを少し、実際のブラウザを動かす E2E テストを最小限にする。

- このリポジトリのコードの大半は自作の部品（`src/sim.js`・`src/ui.js`・`src/scene/`）で、データベースや外部サービスを持たない。入力と結果が決まった小さな部品に分けられるため、単体テストを安く書け、壊れた箇所もすぐ絞れる
- 画面を通すテストは、Chrome の起動と WebGL の描画が要り、遅くて壊れやすい。数を絞り、単体テストで確かめられることを繰り返さない
- 層の名前は、元のピラミッドの名前にこだわらず、リポジトリの中で一貫させる。この文書では「単体・結合・E2E」で統一する
- ほかの戦略（テスティングトロフィーなど）は採らない

出典（2026-11-07 に確認）:

- [Test Pyramid](https://martinfowler.com/bliki/TestPyramid.html)（Martin Fowler、2012-05-01 公開）：画面を通すテストは遅く壊れやすいため、低レベルのテストを多く持つ
- [The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)（Ham Vocke、2018-02-26）：小さく速いテストを多く、E2E は非常に少なくする。層の名前は、一貫していればよい

## 目的

守りたいものは次のとおり。外部との約束（API・データベース）は持たない。

- 運搬シミュレーション（`src/sim.js`）の状態遷移。進捗（`ready`・`total`・`status`）が超過・逆行せず、完了・次のタスク・リセットが決まった順で起きること
- 画面（`src/ui.js`）の表示。注文詳細の値・進捗の割合・検索の絞り込みが、データのとおりに出ること。入力された文字を HTML として解釈しないこと
- データと 3D の取り決め。データのすべてのタスクのゾーンに、3D のピック位置があること
- 3D 部品（`src/scene/`）が、決めた寸法に収まること。荷がパレットからはみ出さず、出荷待機の置き場が重ならないこと

## テストの層

| 層 | 確かめること | 対象 | 道具 | 件数（2026-11-07） |
| --- | --- | --- | --- | --- |
| 単体 | 関数・クラスが、入力に対して決めた結果を返すか。WebGL は使わず、three.js の部品を Node の上で組み立てて、値や数を確かめる | `src/data.js`・`src/sim.js`・`src/ui.js`・`src/scene/props.js`・`src/scene/markers.js`・`src/scene/textures.js` | Vitest・happy-dom | 126 件 |
| 結合 | 実物の部品をつないで動くか。倉庫・フォークリフト・UI・データを組み合わせ、運搬サイクルを通しで回す | `src/scene/warehouse.js` と、`src/sim.js`・`src/ui.js`・`src/data.js` の組み合わせ | Vitest・happy-dom | 13 件 |
| E2E | 利用者の操作の流れが、実際の Chrome で最後まで通るか | 起動・3D のクリック・一覧と検索・運搬の反映・リセット・スマホの幅 | Playwright | 6 件 |

割合は、単体 87%・結合 9%・E2E 4%（全 145 件）。下の層ほど数が多く、速い。E2E が結合より増えたら、E2E で確かめていることを、下の層へ下ろせないかを見直す。

テストの置き場所と、使い方は [環境構築](../runbook/environment-setup.md) にある。

### 単体・結合テストの書き方

- 1 つのテストで、1 つの決めごとを確かめる。名前は「〜のとき〜になる」の形で、日本語で書く
- 乱数は `seeded`（`src/scene/props.js`）で固定し、時刻は Vitest の偽の時計で進める。実時間を待たない
- シミュレーションは、`tests/helpers/fixtures.js` の `runUntil` で時間を進める。タスクは `cloneTasks` で複製する。シミュレーションが値を書き換えるため
- canvas は、`tests/setup.js` の代用品で受け流す。happy-dom は 2D コンテキストを返さないため
- UI のテストは、`tests/helpers/dom.js` で、実物の `index.html` のマークアップを読み込む

### E2E テストの書き方

- `window.__app`（`src/main.js`。開発サーバーのときだけ公開される）で、3D のパレットを画面の座標に変換し、実際のマウスで押す
- ソフトウェア描画は 1 fps ほどしか出ないため、運搬やカメラの移動は、ページの中で時間を進めて早送りする
- 各テストの最後に、コンソールのエラー・警告が 0 件であることを確かめる

### テストしないもの

- `src/main.js`・`src/scene/stage.js`：WebGL のレンダラーを作るため、Node では動かない。E2E が通ることで確かめる。カバレッジの対象外にしている
- 3D の見た目（影・配置・色・重なり）：機械では判断できない。人が確かめる

## 機械と人の分担

- 機械で確かめられることは、機械に任せる。人の確かめはばらつくため
- 人は、機械では確かめにくいこと（仕様の解釈が合っているか・使い勝手・見た目）を確かめる

人が確かめること:

- 3D の見た目（影・荷の置き方・床の文字・重なり）。画面左下の Reference ボタンで `sample.jpg` を重ねて見比べる
- 画面の使い勝手。[使い方](../runbook/usage.md) の操作を一通り行い、表示と動きに違和感が無いか
- 狭い画面（幅 900 px 以下）での配置
- 画面を大きく変えたときの、手元のブラウザ（Claude in Chrome など）での操作の確認

## いつ動かすか

| タイミング | 動かすもの |
| --- | --- |
| 編集の後 | Lint・整形（`lefthook.yml` の `claude-edit`） |
| コミットの前 | `npm run lint`・`npm run format:check`・`npm test`（5 秒ほど） |
| 画面を変えたとき | `npm run test:e2e`（1 分半ほど。Chrome が要る） |
| PR の CI | なし。`.github/` を入れていない。入れるときは、`npm test` を流す |

## AI が書いたテストの扱い

- テストの観点（何を確かめるか）は、人が読んで足りているかを確かめる。AI は、実装に合わせてテストを書き、間違った挙動を正として固めてしまうことがあるため
- 落ちたテストを通すために、テストのほうを書き換えるときは、理由を PR に書く
- AI が書いたテストは、実装を一時的に壊して（変異）、落ちることを確かめる。通るだけで、何も守っていないテストを見つけるため。壊したら、必ず元に戻し、差分が空であることを確かめる

## テストデータと環境

- データ：`src/data.js` の `TASKS`・`KPI`（固定値）を使う。テストは `structuredClone` で複製して書き換え、元の値を変えない
- 乱数と時刻：固定する（上の「単体・結合テストの書き方」）
- 環境：ローカルだけ。Node 22.12 以上（Vitest 5 の要件）。単体・結合は happy-dom、E2E は手元の Chrome を使う。Playwright は、ブラウザ本体を取得しない
- 本番のデータや秘密は使わない。そもそも持たない

## 完了の基準

- `npm test` がすべて通る
- `npm run test:coverage` が通る。`vitest.config.js` の下限（命令・関数・行が 95%、分岐が 85%）を下回らない。対象は `src/` のうち `main.js` と `scene/stage.js` を除いたもの
- 画面を変えたときは、`npm run test:e2e` が通る
- `npm run lint` と `npm run format:check` が通る
- 新しい機能と不具合の修正には、まず単体テストを足す。画面を通さないと確かめられないときだけ、E2E を足す
- 不具合を直すときは、直す前に落ちるテストを書き、直した後に通ることを確かめる
